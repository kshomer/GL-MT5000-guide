# Резервный доступ к роутеру: роутер как WireGuard-клиент VPS

Как обеспечить доступ к домашнему роутеру из любой точки мира, не завися от белого IP
и входящих подключений: роутер сам устанавливает исходящее соединение к VPS, а управление
идёт через эту же сеть.

Также разбирается, как этот путь соотносится с обычным ([WireGuard-сервер на самом
роутере](18-wireguard-server.md)), что доступно через каждый из них и как добраться
до устройств домашней сети — включая проброс портов, когда прямого маршрута нет.

Плейсхолдеры: `<SERVER_IP>` — публичный адрес VPS, `<router>` — алиас роутера в ssh-конфиге.
Приватные адреса (10.8.0.x) приводятся как есть — они существуют только внутри VPN-сети.

---

## 1. Зачем это нужно

Обычный сценарий удалённого доступа — [WireGuard-сервер на самом роутере](18-wireguard-server.md):
подключение из-за границы на домашний белый IP, попадание в домашнюю сеть. Работает,
пока выполняются два условия:

- у домашнего подключения есть белый IP;
- провайдер пропускает входящие на порт WireGuard.

Оба условия внешние и могут исчезнуть: провайдер переведёт абонентов за NAT, заблокирует
UDP-порт, или белый IP просто перестанут выдавать. Тогда доступ к роутеру теряется —
а починить его удалённо уже нечем.

Резервный путь снимает эту зависимость: **роутер сам звонит наружу**, устанавливая
исходящее соединение к VPS. Исходящие блокировать заметно сложнее, чем входящие,
и белый IP для них не нужен вовсе.

```
обычный путь:   клиент → домашний белый IP → роутер          (зависит от провайдера)
резервный путь: клиент → VPS ← роутер (дозвонился сам)       (не зависит)
```

---

## 2. Схема

На VPS уже работает WireGuard-сервер (в примере — wg-easy в Docker) с сетью `10.8.0.0/24`.
Роутер становится ещё одним его клиентом, получая адрес `10.8.0.2`.

```
VPS: WireGuard-сервер 10.8.0.1
      ├── клиент 10.8.0.2  ← роутер (интерфейс wg1)
      └── клиент 10.8.0.X  ← ноутбук/телефон
```

Подключение клиентом переносит в одну сеть с роутером — он становится доступен по
`10.8.0.2`.

⚠️ На роутере это **второй** WireGuard-интерфейс. Первый (`wg0`) работает в роли сервера
для домашнего доступа — они не конфликтуют и работают одновременно.

## 3. Настройка

### Шаг 3.1 — Создать клиента на VPS

В панели WireGuard-сервера создать нового клиента (например с именем `router`) и скачать
его конфигурационный файл. Он выглядит примерно так:

```
[Interface]
PrivateKey = <приватный ключ клиента>
Address = 10.8.0.2/32, fdcc:...::cafe:2/128
MTU = 1420
DNS = 1.1.1.1, 2606:4700:4700::1111

[Peer]
PublicKey = <публичный ключ сервера>
PresharedKey = <общий ключ>
AllowedIPs = 0.0.0.0/0, ::/0
PersistentKeepalive = 0
Endpoint = <SERVER_IP>:51820
```

### Шаг 3.2 — Что изменить при переносе на роутер

Конфиг от панели рассчитан на обычного клиента, которому нужен весь трафик через VPN.
Для роутера три параметра надо изменить, иначе сломается его основная работа:

| Параметр в конфиге        | На роутере               | Почему                                                               |
| ------------------------- | ------------------------ | -------------------------------------------------------------------- |
| `AllowedIPs = 0.0.0.0/0`  | **только `10.8.0.0/24`** | иначе весь трафик роутера уйдёт в этот туннель и сломает прокси-стек |
| `PersistentKeepalive = 0` | **`25`**                 | без удержания соединение простаивает, и снаружи не достучаться       |
| `DNS = ...`               | **не переносить**        | у роутера свой резолвер                                              |

IPv6-адрес тоже можно не переносить — для управления он не нужен.

`AllowedIPs` — самый важный пункт. Он означает «какие адреса маршрутизировать в этот
туннель». Оставив `0.0.0.0/0`, роутер начнёт гнать туда весь свой трафик.

### Шаг 3.3 — Создать интерфейс на роутере (OpenWrt)

```sh
uci set network.wg1=interface
uci set network.wg1.proto='wireguard'
uci set network.wg1.private_key='<PrivateKey из конфига>'
uci add_list network.wg1.addresses='10.8.0.2/32'
uci set network.wg1.mtu='1420'

uci add network wireguard_wg1
uci set network.@wireguard_wg1[-1].description='vps-wg'
uci set network.@wireguard_wg1[-1].public_key='<PublicKey сервера>'
uci set network.@wireguard_wg1[-1].preshared_key='<PresharedKey>'
uci add_list network.@wireguard_wg1[-1].allowed_ips='10.8.0.0/24'
uci set network.@wireguard_wg1[-1].endpoint_host='<SERVER_IP>'
uci set network.@wireguard_wg1[-1].endpoint_port='51820'
uci set network.@wireguard_wg1[-1].persistent_keepalive='25'
uci set network.@wireguard_wg1[-1].route_allowed_ips='1'

uci changes | grep -v key        # проверить перед применением
```

### Шаг 3.4 — Firewall

Без этого SSH через новый интерфейс не пройдёт: зона по умолчанию отбрасывает входящие.

```sh
uci add_list firewall.@zone[0].network='wg1'
uci commit firewall
uci commit network
/etc/init.d/network restart
```

Здесь `@zone[0]` — зона `lan`. Проверить, что это действительно она:

```sh
uci show firewall | grep -E "zone\[0\].(name|network)"
```

⚠️ `network restart` разрывает текущее SSH-соединение — переподключиться.

## 4. Проверка

### На роутере

```sh
ip -br addr show wg1          # ожидается: wg1 UNKNOWN 10.8.0.2/32
wg show wg1                   # должна быть строка latest handshake и растущий transfer
ip route | grep 10.8.0        # маршрут 10.8.0.0/24 dev wg1
ping -c 3 10.8.0.1            # сервер в VPN-сети
```

⚠️ **Ловушка в пинге.** Если интерфейс не поднялся, пакет уходит по маршруту по умолчанию,
и ответить может постороннее устройство в сети провайдера. Признак подделки — слишком
маленькая задержка (1-2 мс вместо реальной до сервера) и нетипичный TTL. Реальный ответ
через туннель приходит с задержкой, соответствующей расстоянию до VPS.

### На VPS

⚠️ Если WireGuard-сервер работает в контейнере, интерфейс `wg0` существует только внутри
него. С хоста пинг клиента не пройдёт — и это не ошибка настройки. Проверять надо изнутри:

```sh
docker exec <wg-контейнер> ping -c 3 10.8.0.2
docker exec <wg-контейнер> sh -c 'nc -zv 10.8.0.2 22'
```

### Полная проверка сценария

Настоящий тест — с другого канала связи, имитируя нахождение вне дома:

1. подключить ноутбук к мобильному интернету, отключив домашнюю сеть;
2. убедиться, что путь действительно другой: `curl -s https://api.ipify.org`;
3. включить свой клиентский WireGuard-конфиг;
4. проверить:

```sh
ping -c 3 10.8.0.1
ping -c 3 10.8.0.2
ssh root@10.8.0.2 "uptime"
```

Признаки успеха: пинги проходят с задержкой мобильного канала (не локальной сети),
у роутера TTL на единицу меньше, чем у сервера (пакет прошёл через него), SSH подключается.

## 5. Как пользоваться

### Два пути и что через какой доступно

Оба способа работают параллельно и не мешают друг другу.

|                           | Путь 1: WireGuard на роутере  | Путь 2: через VPS             |
| ------------------------- | ----------------------------- | ----------------------------- |
| Интерфейс на роутере      | `wg0` (роутер в роли сервера) | `wg1` (роутер в роли клиента) |
| Куда подключается клиент  | домашний белый IP             | VPS                           |
| Сеть                      | 10.0.100.0/24                 | 10.8.0.0/24                   |
| Адрес роутера             | 10.0.100.1                    | 10.8.0.2                      |
| Доступна ли домашняя сеть | **да, вся** (192.168.x.x)     | нет, только роутер            |
| Зависит от                | белого IP + входящего UDP     | доступности VPS               |

Путь 1 даёт больше — доступна вся домашняя сеть. Путь 2 устойчивее — работает,
даже если провайдер заберёт белый IP или закроет входящие.

### Алиасы в ~/.ssh/config

Удобно завести оба и назвать так, чтобы было понятно, какой путь используется:

```ini
Host router-wg0
    HostName 10.0.100.1
    User root
    IdentityFile ~/.ssh/id_ed25519_servers

Host router-wg1
    HostName 10.8.0.2
    User root
    IdentityFile ~/.ssh/id_ed25519_servers
```

Проверить, какие параметры применятся:

```sh
ssh -G router-wg0 | grep hostname
```

### Доступ к устройствам домашней сети (только через путь 1)

Подключение по пути 1 переносит во всю домашнюю сеть — устройства доступны по обычным
адресам.

**Точка доступа MikroTik:** подключаться через Winbox, в поле «Connect To» указывать
**IP-адрес** устройства, а не MAC.

⚠️ Winbox по MAC-адресу работает только в пределах одной локальной сети — это канальный
уровень, такие кадры не проходят через маршрутизатор. Удалённо — исключительно по IP.

⚠️ Если на устройстве в целях безопасности отключены лишние сервисы (ssh, www, telnet,
api), останется только штатный порт управления. Проверить, что отвечает:

```sh
timeout 5 nc <IP-устройства> 8291 < /dev/null && echo "порт управления открыт"
```

### Почему через путь 2 домашняя сеть недоступна

Это следствие настройки `AllowedIPs = 10.8.0.0/24` (см. шаг 3.2), и решение сознательное.

В конфиге от панели стояло `AllowedIPs = 0.0.0.0/0` — «маршрутизировать в туннель весь
трафик». Для обычного клиента это и есть смысл VPN. Но на роутере такое значение означало
бы, что весь его исходящий трафик уходит в туннель к VPS — включая обращения самого
прокси-клиента к своему серверу. Получается петля: прокси пытается достучаться до сервера,
а его соединение заворачивается в другой туннель к тому же серверу. Схема разваливается.

Поэтому маршрутизируется только подсеть VPN. Домашняя сеть (192.168.x.x) через этот
туннель не проходит — не потому что заблокирована, а потому что маршрута нет.

Расширить можно (прописать домашнюю подсеть на сервере, роутере и клиенте), но это
несколько связанных правок в работающей схеме. Есть способ проще.

### Доступ к домашним устройствам через путь 2: проброс порта по SSH

SSH умеет пробрасывать порт удалённого устройства на локальную машину. Соединение идёт
через роутер, никаких правок в конфигурации не требуется.

```sh
ssh -L 8291:<IP-устройства>:8291 router-wg1
```

Окно с этой сессией оставить открытым — туннель живёт, пока она не закрыта.
Затем в программе управления подключаться к `127.0.0.1:8291`.

Как это работает:

```
клиент на компьютере → localhost:8291 → SSH-туннель → роутер → устройство:8291
```

Проверить, что туннель поднялся:

```sh
lsof -i :8291 | head -3        # должен слушать процесс ssh
```

**Чтобы не набирать каждый раз** — прописать проброс в алиас:

```ini
Host router-wg1
    HostName 10.8.0.2
    User root
    IdentityFile ~/.ssh/id_ed25519_servers
    LocalForward 8291 <IP-устройства>:8291
```

Тогда при любом подключении по этому алиасу порт пробрасывается автоматически.

Проверка:

```sh
ssh -G router-wg1 | grep localforward
```

⚠️ Две одновременные сессии по этому алиасу конфликтуют за локальный порт: вторая
подключится, но выведет предупреждение и туннель не создаст.

Тем же способом пробрасывается любой другой порт любого устройства домашней сети —
достаточно поменять номер и адрес.

### С чужого устройства

1. установить клиент WireGuard;
2. импортировать заранее сохранённый конфиг;
3. включить туннель;
4. `ssh root@<адрес роутера>`, войти по паролю.

Веб-интерфейс роутера при необходимости: `http://<адрес роутера>`.

⚠️ **Адреса 10.0.100.1 и 10.8.0.2 доступны только при активном VPN-подключении.** Без
туннеля это приватные адреса, которые никуда не ведут.

## 6. Что подготовить заранее

Главная ловушка этой схемы — замкнутый круг: чтобы скачать клиентский конфиг из панели
WireGuard-сервера, обычно нужен SSH-туннель к VPS, а для него — рабочее подключение.
Оказавшись в поездке без сохранённого конфига, получить его будет негде.

Поэтому до отъезда:

- сохранить клиентский конфиг (или QR-код) в надёжном месте: менеджер паролей,
  зашифрованный архив, распечатка;
- проверить подключение с другого канала связи — не откладывая до момента, когда
  оно понадобится;
- убедиться, что известен пароль роутера (если ключа под рукой не будет);
- записать пароли и адреса устройств домашней сети — пароль сетевого оборудования
  хранится в виде хеша и восстановлению не подлежит, только сбросу. Если возникает вопрос
  «какой там пароль» — сменить его заранее, пока доступ есть, и сохранить;
- сохранить конфиги обоих путей, а не только одного;
- держать копию SSH-ключей в зашифрованном виде.

---

## 7. Что стоит понимать

**Два пути независимы.** Прямой WireGuard на домашний IP и путь через VPS работают
параллельно. Отказ одного не влияет на другой — в этом весь смысл.

**Резервный путь зависит от VPS.** Если сервер недоступен или туннель не поднялся,
этот способ не сработает. Полностью безотказных схем не бывает; задача — не иметь
единой точки отказа.

**Keepalive обязателен.** Без него соединение простаивает, запись о клиенте на сервере
устаревает, и достучаться до роутера снаружи не выйдет. Значение 25 секунд — стандартная
практика для клиентов за NAT.

**Прокси-стек не затронут.** Если правила прозрачного проксирования применяются только
к конкретным интерфейсам, новый интерфейс в них не попадает — управляющий трафик идёт
напрямую, а не через прокси. Проверить, что нового интерфейса нет в правилах перехвата:

```sh
iptables -t mangle -S PREROUTING | grep <цепочка-прокси>
```
