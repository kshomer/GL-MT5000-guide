# Tailscale exit node на роутере: попытка настройки и причина отказа

Документ описывает попытку настроить Tailscale exit node на роутере GL-MT5000.
Цель: доступ к домашней сети и выход в интернет через настроенный дома Xray, из
любой точки мира. Работа прошла через каскад проблем, каждая из которых
потребовала отдельной диагностики. В итоге Tailscale удалён с роутера, но по
пути получены ценные знания и сделано ключевое открытие (рабочий белый IP),
изменившее весь дальнейший подход — см. отдельный документ про
[WireGuard-сервер](18-wireguard-server.md).

Плейсхолдеры: `<SERVER_IP>` — адрес VDS, `<HOME_WHITE_IP>` — белый статический IP дома.

---

## 1. Изначальная цель

С мобильного интернета (вне дома) иметь возможность:

- подключаться к домашней сети,
- выходить в интернет (РФ и загран) через настроенный дома Xray.

Идея: телефон → Tailscale → домашний роутер (exit node) → Xray → интернет.

---

## 2. Хронология проблем и решений

### Проблема 1: флаг --accept-routes ломал интернет

При первой команде `tailscale up --accept-routes --advertise-exit-node` интернет
полностью падал. Причина: `--accept-routes` заставлял роутер принимать маршруты из
Tailscale (включая `0.0.0.0/0`), создавая петлю/конфликт с основным выходом.

**Решение:** убрать `--accept-routes`. Для exit node он не нужен — нужен только
`--advertise-exit-node --accept-dns=false`.

### Проблема 2: OOM (Out Of Memory) — Xray убивался ядром

Симптом: «то работает, то нет». Xray падал, procd перезапускал, снова падал (crash loop).

Диагностика (мониторинг памяти + logread): Xray раздувался с ~40 МБ до 645 МБ за
секунды, ядро убивало его (`Out of memory: Killed process xray, anon-rss:645404kB`).

**Механизм:** tproxy перехватывал `-j XRAY` со всех интерфейсов, включая
`tailscale0`. Трафик exit node (от телефона) заворачивался в Xray → лавина
соединений → OOM.

**Решение (ключевое):** ограничить перехват tproxy только LAN-интерфейсом:
`iptables -t mangle -A PREROUTING -i br-lan -j XRAY` (вместо перехвата со всех
интерфейсов). Так трафик `tailscale0` больше не попадает в tproxy. Проверено: RSS
Xray под нагрузкой exit node стал стабильным ~45 МБ (был 645 МБ). OOM побеждён.

**Ложный след — лимит открытых файлов.** По пути был симптом `too many open
files`. Лимит поднят с 4096 до 65535 — это убрало предохранитель и усугубило
OOM (Xray смог открыть больше соединений → больше памяти). Итог: возврат на
16384 — баланс (хватает для нормальной работы, но ограничивает аппетит, чтобы
аномалия не вызвала OOM). Это значение осталось в `init.d/xray-tproxy` как
правильное для 1 ГБ RAM.

### Проблема 3: накопление TIME_WAIT

При множественных рестартах сервиса (которых было много за отладку) с активным
трафиком накапливались TIME_WAIT-соединения к серверу (до 1300+), исчерпывая
исходящие порты → туннель не поднимался.

**Решение:** очистка TIME_WAIT встроена в `tproxy-apply.sh`
(`conntrack -D -d <SERVER_IP> -p tcp --state TIME_WAIT`). В обычной жизни (без
десятков рестартов подряд) проблема не возникает.

### Проблема 4: трафик телефона не выходил в WAN

После настройки exit node трафик от телефона (`tailscale0`) не выходил в
интернет — SYN уходил, но соединения повисали. Причина: не было правил forward
`tailscale0` → WAN.

**Решение:** добавлены правила forward (`tailscale0` ↔ `eth1`) + masquerade для
`100.64.0.0/10`. Экспериментальные правила, при откате удалены.

### Проблема 5: DNS телефона через exit node не работал

Телефон не резолвил имена → сайты по именам не открывались (только приложения с
захардкоженными IP слали трафик). Причина: DNS-цепочка через exit node разорвана
(`--accept-dns=false` на роутере + телефон не использовал Tailscale DNS).

**Решение:** на телефоне включить «Use Tailscale DNS Settings» → российские сайты
заработали.

### Проблема 6: заграничный трафик телефона шёл мимо Xray

После исключения `tailscale0` из tproxy (против OOM) заграничный трафик телефона
шёл напрямую через провайдера → упирался в блокировки. Показывал домашний IP, а
не VDS.

**Решение:** добавить перехват `tailscale0` в цепочку `XRAY`, но только когда
телефон в локальной сети (Wi-Fi). Проверено с мониторингом памяти: заворот
`tailscale0` в Xray работал стабильно (RSS ~48 МБ под видеонагрузкой — несколько
видео в YouTube 4K одновременно с Instagram, OOM не вернулся).

**Результат:** по Wi-Fi телефон → дом → Xray → заграница заработал (эстонский IP,
российские и заграничные сайты — оба варианта).

---

## 3. Что достигнуто

- OOM полностью побеждён (ключевое: `-i br-lan` разделяет трафик tproxy и `tailscale0`).
- Exit node полностью работает по Wi-Fi (когда телефон в домашней сети): телефон и
  другие устройства получают эстонский IP на загранице, российские сайты — напрямую
  через Xray, YouTube/Instagram работают.
- Заворот заграничного трафика в Xray стабилен под нагрузкой (память ровная).
- Доступ к домашней сети с устройств в сети.

---

## 4. Финальная проблема

**Exit node с мобильного интернета не работал.** Причина — двойной CGNAT:
телефон за CGNAT мобильного оператора, роутер (на тот момент считался) тоже за
CGNAT провайдера. Прямое P2P невозможно, связь только через DERP-релей, и
`tailscale ping` с мобильного давал timeout — надёжная связь для exit node не
устанавливалась.

Вывод на тот момент: упор в физику сетей (двойной CGNAT), не в настройку.

По итогу принято решение: отказаться от Tailscale, откатить его с роутера и
использовать белый статический IP напрямую с WireGuard.

---

## 5. Ключевое открытие: белый IP на самом деле работает

После отката Tailscale обнаружено: у роутера есть рабочий белый статический IP от
провайдера (`<HOME_WHITE_IP>`, бизнес-статик, без дополнительной платы, бессрочно).

Важный нюанс: на WAN роутера стоит приватный адрес (proto static), а наружу
роутер выходит именно этим белым IP. Похоже на CGNAT — но проверка входящих
доказала обратное:

**Тест** (с внешнего VPS `<SERVER_IP>`): `curl http://<HOME_WHITE_IP>/` → вернулась
веб-панель роутера (HTTP 200, Admin Panel). Значит входящие соединения на белый IP
доходят до роутера — он полноценный на вход. (SSH-порт 22 давал timeout, но это
firewall роутера блокирует 22 с WAN, а не провайдер — порт 80 прошёл.)

**Следствие:** Отказ от настройки Tailscale через мнимый CGNAT — рабочий вариант — использование белого IP. С ним правильное решение — прямой VPN-сервер на роутере (WireGuard), к которому телефон подключается напрямую по белому IP, без Tailscale, без DERP, без двойного CGNAT (см. [WireGuard-сервер](18-wireguard-server.md)).

Если провайдер отключит белый IP — параллельно настроен независимый резервный
доступ через VPS, см.
[«Роутер как WireGuard-клиент VPS»](19-router-as-wg-client.md).

---

## 6. Условия для возврата к Tailscale в будущем

Стоит пробовать снова, если:

- появится необходимость именно в Tailscale (mesh-сеть многих устройств);
- либо Tailscale выйдет из беты на GL.iNet (сейчас бета, в будущих прошивках
  может улучшиться);
- либо появится более мощный роутер (MT5000 на 1 ГБ RAM на пределе с exit node +
  tproxy одновременно).

Наработки этого документа (особенно `-i br-lan` против OOM) применимы при
повторе. Но с рабочим белым IP Tailscale, скорее всего, не нужен — прямой
VPN-сервер лучше (см. [WireGuard-сервер](18-wireguard-server.md)).

---

## 7. Технические артефакты, оставшиеся полезными

- `tproxy-apply.sh` с `-i br-lan` — перехват только из LAN, оставлено как основная
  практика (защита от попадания постороннего трафика в tproxy).
- Хук `firewall.user` — переприменяет tproxy при reload fw3.
- Лимит `nofile=16384` в `init.d/xray-tproxy` — баланс для 1 ГБ RAM.
- Очистка TIME_WAIT в `tproxy-apply.sh` — защита от накопления.
- Исключение `100.64.0.0/10` из цепочки `XRAY` — убрано при откате, было нужно
  только для Tailscale.

---

## 8. Итог

Tailscale полностью удалён с роутера, основной VPN-стек остался цел и рабочим.

Мобильный сценарий через Tailscale не был достигнут (двойной CGNAT), но:

- технически exit node был настроен и работал по Wi-Fi (доказано);
- побеждён сложный OOM;

Дальнейший шаг — использовать белый IP напрямую: WireGuard-сервер на роутере для
доступа к дому с мобильного и внешних сетей, без посредников. Процедура полного
отката Tailscale, если понадобится, описана в [отдельном документе](17-tailscale-rollback.md).

## 8. Обновление информации

Судя по всему в версии роутера V4.9.0 проблемы с tailscale устранены.
