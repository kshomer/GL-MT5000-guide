# MT5000 — настройка Xray (Reality+Vision) + tproxy. Детальный отчёт

Документ описывает всё, что происходило **после** перевода GL-MT5000 на Global-прошивку:
установку Xray-клиента на роутере, поднятие tproxy, диагностику проблемы и её решение.
Составлен так, чтобы им мог воспользоваться любой человек для изучения — как справочник и как карта уже пройденных
(в том числе тупиковых) путей.

Принцип документа: **разделять доказанные факты и гипотезы.** Где написано «доказано» —
это подтверждено прямым тестом. Где «гипотеза» — это правдоподобное объяснение, которое
не проверялось до конца.

Плейсхолдеры: `<SERVER_IP>` — адрес VDS-сервера, `<HOME_WHITE_IP>` — белый статический IP
дома, `<REALITY_SNI>` — целевой узел Reality (SNI), `<ISP_DNS_STUB_IP>` — адрес,
который вышестоящий DNS возвращает вместо реального.

## 1. Установка Xray-клиента на роутер (прошло без проблем)

1. Проверено наличие модулей tproxy — **всё уже было в системе**, доустанавливать не пришлось:
   `iptables-mod-tproxy`, `kmod-ipt-tproxy`, `kmod-nf-conntrack`.
2. Firewall-бэкенд — iptables (fw3). Значит tproxy-правила пишем на iptables.
3. Скачан бинарь `Xray-linux-arm64-v8a.zip` (v26.6.27) с релизов XTLS. В архиве оказались
   и бинарь `xray`, и geodata (`geoip.dat`, `geosite.dat`).
4. Использована **geodata от Loyalsoldier** (расширенные списки), а не из архива.
   Путь: `/opt/xray/share/`. Обязательна переменная `XRAY_LOCATION_ASSET=/opt/xray/share`.
5. Структура на роутере: бинарь `/opt/xray/bin/xray`, конфиг `/opt/xray/config/client.json`,
   логи `/opt/xray/log/`, geodata `/opt/xray/share/`.

Важная деталь окружения (overlay): файлы в `/opt/...` физически лежат в
`/overlay/upper/opt/...` — `find` показывает их дважды, но это один и тот же файл, не дубликат.

## 2. tproxy — механизм перехвата (работал корректно с самого начала)

Схема: `dokodemo-door` inbound на порту `12345` с `tproxy` + policy-routing (метка 1, таблица 100).
Правила применяются идемпотентным скриптом `/opt/xray/tproxy-apply.sh` (включён в этот
репозиторий: `scripts/01-tproxy-apply.sh`) — безопасен для повторного запуска, адрес сервера
читает динамически из конфига, а не захардкожен.

Правила (iptables mangle):

- цепочка `XRAY` в `PREROUTING`;
- исключения `RETURN` для локальных/служебных сетей (`10/8`, `192.168/16`, `127/8`, и т.д.) —
  **это защищает SSH и LAN от заворота в туннель**;
- исключение `RETURN` для IP самого сервера `<SERVER_IP>` — чтобы туннель не зациклился;
- `TPROXY --on-port 12345 --tproxy-mark 1` для остального TCP/UDP.

policy-routing:

```sh
ip rule add fwmark 1 table 100
ip route add local 0.0.0.0/0 dev lo table 100
```

**Скрипт отката** `/opt/xray/tproxy-flush.sh` (в этом репозитории: `scripts/02-tproxy-flush.sh`)
снимает все правила и маршруты одной командой.
Страховка при применении правил — вторая открытая SSH-сессия (на случай потери связи в первой).

Проверка счётчиков подтвердила: перехват работал, исключения отрабатывали правильно
(адреса локального списка шли в `RETURN`, остальное — в `TPROXY`).

## 3. Проблема

Симптом: базовый туннель работал (одиночные запросы проходили), но **реальный сёрфинг
и нагрузка ломались** — внешние домены не открывались стабильно.

Точная воспроизводимая картина (доказано тестами):

- одиночный запрос через туннель — **проходит** (6/6);
- залп из 20 параллельных запросов — **100% fail** (20/20 таймаут);
- сразу после залпа даже одиночный запрос временно падает, через ~минуту снова работает;
- на сервере в логах: сначала `REALITY: processed invalid connection ... failed to read
client hello`, затем (в другом тесте) `authentication failed or validation criteria not met`.

## 4. Проверенные и отброшенные гипотезы (карта тупиковых путей)

Это самая ценная часть для будущего — чтобы не повторять уже отработанные ложные направления.
Каждая гипотеза была отброшена **фактом**, а не догадкой.

| #   | Гипотеза                                 | Как проверялась                                        | Результат — почему отброшена                                                                                                                      |
| --- | ---------------------------------------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Версия Xray-клиента (26.6.27 бажная)     | Откат клиента на v25.10.15                             | Не помогло — та же проблема. **Версия ни при чём.**                                                                                               |
| 2   | Обвязка (tproxy/sniffing/routing)        | Собран голый minimal-конфиг (только socks+outbound)    | Голый туннель тоже нестабилен под нагрузкой. **Обвязка ни при чём.**                                                                              |
| 3   | Рассинхрон времени (Reality maxTimeDiff) | `date -u` на роутере и сервере                         | Разница пара секунд. **Время ни при чём.**                                                                                                        |
| 4   | MTU / фрагментация ClientHello           | tcpdump на WAN                                         | ClientHello (1724 б) уходит целиком, сервер подтверждает приём. **MTU ни при чём.**                                                               |
| 5   | Нехватка ресурсов сервера                | `docker stats`, лимит nofile                           | CPU 0.04%, RAM 11 МБ, nofile 524k/открыто 7. **Сервер не перегружен.**                                                                            |

| 7   | Лавину создаёт tproxy (весь LAN)         | Тест голого туннеля без tproxy, socks-порт             | 20 параллельных валятся и без tproxy. **tproxy ни при чём.**                                                                                      |

| 9   | sockopt tcpNoDelay на outbound           | minimal2 с `tcpNoDelay: true`                          | 20/20 fail. **tcpNoDelay сам по себе не решает.**                                                                                                 |

Опорные факты, которые всё это время оставались стабильными и в итоге указали на причину:

- **openssl-лавина (чистый TLS) к `<SERVER_IP>` проходит 20/20** — сеть/сервер держат нагрузку;
- **Shadowrocket** дома, тот же канал, тот же сервер, Reality+Vision — **стабилен**;
- **sing-box** ранее на этом же роутере/сервере/канале с Reality+Vision — **работал под нагрузкой**;
- ошибка на сервере сменилась с `failed to read client hello` на `authentication failed` —
  это перевело поиск с «сеть/чтение» на «верификация Reality», т.е. на **параметры клиента**.

## 5. Найденная причина (доказано чистым A/B тестом) и решение

**Причина: параметр `fingerprint: "chrome"` в `realitySettings` клиентского конфига.**
**`chrome` под лавиной одновременных соединений массово ломается, `randomized` — нет.**

### Итоговое доказательство — чистый A/B тест

Ранние тесты (просто curl-залпы) были зашумлены «остыванием» сервера, поэтому давали
противоречивые цифры. Финальный тест устранил шум: **случайный перемешанный порядок**
chrome/randomized + **адаптивное ожидание остывания** перед каждым залпом (каждый залп
стартует с одинаково «свежего» сервера) + по 4 прогона каждого fingerprint.

Результат (залп 20 параллельных соединений на каждый прогон):

| Прогон | Fingerprint | Результат | Ожидание остывания |
| ------ | ----------- | --------- | ------------------ |
| 1      | randomized  | 20/20 ok  | 0 циклов           |
| 2      | chrome      | 1/20 ok   | 0 циклов           |
| 3      | randomized  | 20/20 ok  | 0 циклов           |
| 4      | chrome      | 0/20 ok   | 4 цикла            |
| 5      | chrome      | 0/20 ok   | 6 циклов           |
| 6      | randomized  | 20/20 ok  | 0 циклов           |
| 7      | randomized  | 20/20 ok  | 0 циклов           |
| 8      | chrome      | 0/20 ok   | 3 цикла            |

**Сводка: randomized → 80/80 ok (100%). chrome → 1/80 ok (~1%).**

Критерии интерпретации были зафиксированы **до** теста. Результат однозначно попал в
первый: chrome систематически проваливается, randomized стабилен, при равном свежем старте.
**Вывод: fingerprint — реальный фактор. Решение с randomized надёжно, а не случайно.**

Дополнительное подтверждение механизма — колонка «ожидание остывания»:

- перед каждым randomized-прогоном ожидание = 0 (сервер всегда свежий);
- перед chrome-прогонами 4/5/8 ожидание 3–6 циклов, т.к. им предшествовали chrome-прогоны,
  которые **сами** завалили сервер в остывание.
- Прогон 2 решающий: chrome стартовал с 0 остывания (сервер свежий после randomized) и всё
  равно дал 1/20. Значит остывание — **следствие** провалов chrome, а не их причина.

### Что доказано и что осталось неизвестным

**Доказано:** проблема воспроизводимо привязана к `chrome` и воспроизводимо исчезает с
`randomized`. Причина устранена, а не скрыта — она не вернётся.

**Осталось неизвестным (честно):** _почему именно_ на уровне кода uTLS/Reality фиксированный
chrome под лавиной генерирует хендшейки, которые сервер частью отвергает. Точный внутренний
механизм библиотеки не вскрывался. Для практической надёжности это уже неважно.
Не исключены ошибки в самой конфигурации. Глубоких познаний в работе uTLS/Reality — нет. Решение остановиться на `randomized` принято по факту стабильной
работы, а не на основе полного понимания механизма.

### Про тест 3 (серверный лог с `show:true`)

Отдельно проверена серверная сторона — включён `show:true` в `realitySettings` сервера,
зафиксирован лог. Он показал, что **одно** chrome-соединение прошло хендшейк успешно
(`isHandshakeComplete: true`, соединение принято). Сначала это выглядело как противоречие,
но чистый A/B тест всё объяснил: chrome проходит **редко** (~1 из 20 под лавиной) — тест 3
поймал именно такое редкое исключение, а не правило. Противоречия нет.

**Почему Shadowrocket работает с `chrome`, а Xray-клиент — нет (осталось гипотезой):**
вероятно, разная реализация uTLS. Вероятно, Shadowrocket — не на Xray-ядре. На 100% не проверено,
но на решение не влияет.

### Важные follow-up факты про fingerprint

- Fingerprint — **чисто клиентский параметр**. В конфиге сервера его нет, сервер его не
  проверяет. Поэтому клиент на роутере и клиент Shadowrocket настраиваются независимо.
- Скрипт установки VLESS-Reality задаёт `chrome` в **клиентских ссылках** для Shadowrocket —
  там менять не нужно, у Shadowrocket chrome работает.
- На роутере (Xray-клиент) установлен `randomized`.
- `randomized` **не снижает скорость** (fingerprint влияет только на вид хендшейка, не на
  передачу данных) и **не влияет на работу соединения** (каждое соединение — валидный
  отпечаток реального браузера).
- Опасение «при randomized выпадет chrome и сломается» — на практике не подтвердилось:
  проблема была в **массовой одинаковости**, а не в самом chrome; одиночный chrome в потоке
  разных отпечатков безвреден (стресс-тесты прошли чисто).

## 6. Финальный рабочий конфиг роутера (что сейчас стоит и почему)

Файл: `/opt/xray/config/client.json`. Ключевые части и назначение:

- **inbound `tproxy-in`** (порт 12345, dokodemo-door, tproxy, tcp+udp) — приём перехваченного
  трафика от tproxy-правил.
- **sniffing** (`http`, `tls`, `quic`) — обязателен: без него роутинг по доменам не работает,
  Xray подсматривает SNI/host из потока.
- **outbound `proxy`** — VLESS+Reality+Vision на `<SERVER_IP>`:
  - `flow: xtls-rprx-vision`,
  - `security: reality`, `serverName: <REALITY_SNI>`,
  - `publicKey` / `shortId` — из серверного конфига,
  - **`fingerprint: randomized`** ← ключевое исправление (было `chrome`).
- **outbound `direct`** (freedom), **`block`** (blackhole).
- **routing (smart-ru)**: приватные сети + `.ru`/`.su`/`.рф` + `geosite:category-ru` +
  ключевые домены локального списка + `geoip:ru` → `direct`; остальное → `proxy`.

Служебное: `outboundTag` (не `outbound`) в правилах роутинга — иначе `xray -test` ругается
`neither outboundTag nor balancerTag is specified`.

## 7. Что дальше (где искать продолжение)

Фаза установки (рабочий туннель Reality+Vision под нагрузкой) — **завершена и подтверждена
живым трафиком.** Продолжение и связанные темы:

1. **DNS / AdGuard Home.** Провайдер отдаёт **отравленные** ответы: доказано `nslookup` —
   `example.com` и `example.org` резолвятся в один и тот же IP-заглушку
   `<ISP_DNS_STUB_IP>`. Из-за этого часть доменов не открывается даже через
   туннель. Решение — AdGuard Home как локальный резолвер с шифрованным DoH-upstream +
   per-domain правила: см. [DNS/AdGuard + автозапуск](11-dns-adguard-autostart.md).
2. **Точечные исключения в routing** — `.ru`-домены, которые надо гнать **через** туннель,
   а не напрямую (домены, которые требуется направлять через туннель). Реализовано отдельным скриптом
   управления исключениями: см. [xray-route](07-xray-route.md).
3. **Автозапуск** Xray + tproxy при загрузке роутера — реализован через init.d, см. раздел 4
   в [DNS/AdGuard + автозапуск](11-dns-adguard-autostart.md).
4. **Отключение лишних сервисов** (netifyd/gl-dpi и пр.) — см.
   [отдельный документ](20-disabling-unused-services.md).
5. **Удалённый доступ** — рассматривался [Tailscale](16-tailscale-exit-node-attempt.md),
   в итоге выбран [WireGuard](18-wireguard-server.md) (там же объяснение выбора).
6. **Бэкап рабочих конфигов.**

## 8. Краткие выводы (для быстрого чтения)

- Reality+Vision на Xray-клиенте на MT5000 **работает** — под реальной нагрузкой, стабильно.
- Единственное исправление, которое понадобилось: **`fingerprint: chrome` → `randomized`**
  в клиентском конфиге роутера. **Доказано чистым A/B тестом: randomized 80/80 ok,
  chrome 1/80 ok.** Причина реальна и устранена.
- Сервер, сеть, версия Xray, MTU, tproxy, ресурсы — **всё было ни при чём** (проверено
  и отброшено фактами).
- Единственное, что осталось неизвестным, — _почему_ на уровне кода uTLS chrome ломается
  под лавиной. На надёжность решения не влияет.
