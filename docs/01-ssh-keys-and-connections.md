# SSH: полное руководство по ключам и подключениям

Работа с SSH на протяжении всего жизненного цикла: создание ключа, подключение серверов,
удобные алиасы, изменение и удаление записей, отзыв ключей, резервное копирование
и разбор типовых ошибок.

Команды приведены для macOS (там же, где отличия для Linux, это отмечено).

Плейсхолдеры: `<SERVER_IP>` — адрес сервера, `<alias>` — короткое имя, которое
придумывается самостоятельно, `<KEY>` — имя файла ключа.

---

## 1. Что где лежит

Всё хранится в папке `~/.ssh/` на рабочей машине:

| Файл                   | Назначение                                              | Права |
| ---------------------- | ------------------------------------------------------- | ----- |
| `id_ed25519_<имя>`     | **приватный** ключ — секрет, никому не передаётся       | `600` |
| `id_ed25519_<имя>.pub` | **публичный** ключ — копируется на серверы, не секретен | `644` |
| `config`               | алиасы и настройки подключений                          | `600` |
| `known_hosts`          | отпечатки серверов, к которым уже подключались          | `600` |

Разные права у пары ключей — так и должно быть: приватный доступен только владельцу
(иначе SSH откажется его использовать), публичный открыт для чтения.

На сервере публичные ключи лежат в `~/.ssh/authorized_keys` (на OpenWrt/dropbear —
в `/etc/dropbear/authorized_keys`).

---

## 2. Именование ключей

`ssh-keygen` по умолчанию предлагает имя `id_ed25519` — оно одинаково у всех и ничего
не говорит о назначении. Когда ключей несколько, удобнее давать осмысленные имена:
`id_ed25519_servers`, `id_ed25519_work`, `id_ed25519_git`.

Имя файла — просто ярлык, на безопасность не влияет: уникально и секретно **содержимое**
приватного ключа.

**Разделять ключи по назначению** — хорошая практика: если ключ для одного сервиса
утечёт, доступ к остальным сохранится.

---

## 3. Создание ключа

```sh
ssh-keygen -t ed25519 -C "<комментарий>" -f ~/.ssh/id_ed25519_<имя>
```

- `-t ed25519` — современный алгоритм: короткий ключ, быстрый, стойкий (RSA устарел);
- `-C` — метка (комментарий), которая добавляется в конец публичного ключа и видна
  при выводе `ssh-add -l` или в логах сервера при подключении. На саму работу и
  безопасность ключа она не влияет — это чисто справочная информация для человека,
  который потом будет смотреть на список ключей. Разумно указывать назначение и, при
  необходимости, устройство — например `servers-macbook` или `github-work` — чтобы
  через время, глядя на список из нескольких ключей, можно было сразу понять, какой
  для чего;
- `-f` — путь и имя файла.

**Важное уточнение про `<имя>` в этом разделе.** Это не то же самое, что `<alias>` из
раздела 6. `<имя>` — часть имени самого файла ключа на диске (`id_ed25519_<имя>`), она
никогда не вводится в команде `ssh` при подключении — её видно только в файловой
системе, например при `ls ~/.ssh/`. А то, что реально печатается после `ssh` в
терминале (`ssh <alias>`) — это `<alias>`, отдельный ярлык, который задаётся в файле
`~/.ssh/config` (раздел 6) и может называться вообще не так же, как файл ключа. Одно —
про то, как называется файл на диске, другое — как этот доступ вызывается с клавиатуры.

При запросе passphrase рекомендуется задать пароль на ключ. Он шифрует приватный ключ:
даже если файл попадёт к постороннему, без пароля им не воспользоваться.

Появятся два файла: приватный и `.pub`.

---

## 4. Passphrase: сохранение в связку ключей (macOS)

Чтобы не вводить пароль при каждом подключении:

```sh
ssh-add --apple-use-keychain ~/.ssh/id_ed25519_<имя>
```

Пароль запрашивается один раз и сохраняется в Keychain.

На Linux аналог — `ssh-add` + агент (`ssh-agent`), пароль держится до перезагрузки
или до `ssh-add -D`.

Проверить, какие ключи загружены в агент:

```sh
ssh-add -l
```

**Сменить passphrase** (сам ключ не меняется, переустанавливать на серверах не нужно):

```sh
ssh-keygen -p -f ~/.ssh/id_ed25519_<имя>
```

После смены обновить запись в связке:

```sh
ssh-add -d ~/.ssh/id_ed25519_<имя>
ssh-add --apple-use-keychain ~/.ssh/id_ed25519_<имя>
```

## 5. Установка ключа на сервер

```sh
ssh-copy-id -i ~/.ssh/id_ed25519_<имя>.pub root@<SERVER_IP>
```

Запросит текущий пароль сервера — это последний раз, когда он нужен для входа.

**Если `ssh-copy-id` не сработал** (нестандартное хранилище, например OpenWrt/dropbear),
ключ добавляется вручную. Вывести публичный ключ на рабочей машине:

```sh
cat ~/.ssh/id_ed25519_<имя>.pub
```

Скопировать строку целиком и на целевом устройстве добавить её в файл авторизованных
ключей (`~/.ssh/authorized_keys` или `/etc/dropbear/authorized_keys`), затем выставить
права `600` на этот файл.

Проверка входа:

```sh
ssh -i ~/.ssh/id_ed25519_<имя> root@<SERVER_IP> "echo ключ работает"
```

Прошло без запроса пароля — ключ установлен.

## 6. Алиасы: файл ~/.ssh/config

Позволяет подключаться коротким именем и автоматически применять нужный ключ. Чтобы
настроить, нужно открыть файл `~/.ssh/config` (создать, если его ещё нет) и добавить
в него блоки вида:

```ini
Host *
    UseKeychain yes
    AddKeysToAgent yes

Host <alias>
    HostName <SERVER_IP>
    User root
    IdentityFile ~/.ssh/id_ed25519_<имя>

Host <alias-router>
    HostName <ROUTER_IP>
    User root
    IdentityFile ~/.ssh/id_ed25519_<имя>

Host github github.com
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519_git
```

Права на файл:

```sh
chmod 600 ~/.ssh/config
```

Пояснения:

- `Host *` — общие настройки для всех подключений;
- два имени в одной строке (`github github.com`) позволяют и вызывать `ssh github`,
  и корректно работать операциям, которые обращаются к полному имени;
- порядок блоков не важен, но первый совпавший `Host` задаёт параметры.

Полезные дополнительные параметры:

```ini
    Port 2222                              нестандартный порт
    LocalForward 8080 localhost:8080       туннель к порту сервера при подключении
    ServerAliveInterval 60                 держать соединение живым
    IdentitiesOnly yes                     использовать ТОЛЬКО указанный ключ
```

`IdentitiesOnly yes` полезен, когда ключей много: без него SSH перебирает все ключи
из агента и может упереться в лимит попыток аутентификации.

Проверка:

```sh
ssh <alias> "hostname"
```

## 7. Копирование файлов через алиасы

Алиасы работают и в `scp`:

```sh
scp -O <файл> <alias>:/path/            на сервер
scp -O <alias>:/path/<файл> ~/          с сервера
```

Флаг `-O` нужен на свежих версиях macOS (переключает на классический протокол;
многие устройства с busybox не поддерживают новый).

⚠️ В zsh шаблоны в удалённых путях нужно брать в кавычки, иначе оболочка попытается
раскрыть их локально и выдаст «no matches found»:

```sh
scp -O "<alias>:/tmp/backup-*.tar.gz" .
```

## 8. Добавление нового сервера

1. Установить существующий ключ на новый сервер (раздел 5) — отдельный ключ на каждый
   сервер обычно не нужен, достаточно разделения по назначению.
2. Добавить блок в `~/.ssh/config`:

```sh
Host <новый-alias>
    HostName <SERVER_IP>
    User root
    IdentityFile ~/.ssh/id_ed25519_<имя>
```

3. Проверить: `ssh <новый-alias> "hostname"`.

Полезно сразу задать серверу осмысленное имя, чтобы не путаться в консоли:

```sh
hostnamectl set-hostname <имя>
echo "127.0.1.1 <имя>" >> /etc/hosts
```

---

## 9. Изменение записи

Файл `~/.ssh/config` — обычный текст, правится любым редактором:

```sh
nano ~/.ssh/config
```

Частые правки:

- **сменился IP сервера** — поменять `HostName`;
- **переименовать алиас** — поменять значение после `Host`;
- **другой ключ** — поменять `IdentityFile`.

Изменения действуют сразу, перезапускать ничего не нужно.

Проверить, какие параметры реально применятся к алиасу:

```sh
ssh -G <alias> | head -20
```

## 10. Удаление сервера (когда он больше не нужен)

Пример: сервер выведен из эксплуатации, доступ к нему больше не требуется.

**Шаг 1. Убрать алиас из конфига.** Удалить соответствующий блок `Host` из `~/.ssh/config`.

**Шаг 2. Убрать отпечаток из known_hosts:**

```sh
ssh-keygen -R <SERVER_IP>
ssh-keygen -R <имя-хоста-если-было>
```

Иначе при появлении нового сервера на том же адресе SSH выдаст предупреждение
о смене отпечатка.

**Шаг 3. Если сервер продолжает существовать, но доступ нужно закрыть** — удалить свой
публичный ключ из `~/.ssh/authorized_keys` на самом сервере:

```sh
# на сервере
nano ~/.ssh/authorized_keys      # удалить строку со своим ключом
```

Строку можно найти по комментарию в конце ключа.

**Шаг 4. Если сервер удаляется целиком** (у хостера) — достаточно шагов 1-2, ключ
исчезнет вместе с машиной. Отдельно отзывать ничего не требуется.

## 11. Отзыв и замена ключа

Если приватный ключ мог быть скомпрометирован (потеря устройства, утечка файла):

1. **Создать новый ключ** (раздел 3) с другим именем.
2. **Установить его на все серверы** (раздел 5) — пока старый ещё работает.
3. **Проверить вход по новому** на каждом сервере.
4. **Удалить старый публичный ключ** из `authorized_keys` на каждом сервере.
5. **Обновить `~/.ssh/config`** — заменить `IdentityFile` на новый ключ.
6. **Удалить старый ключ** локально:

```sh
ssh-add -d ~/.ssh/id_ed25519_<старое>
rm ~/.ssh/id_ed25519_<старое> ~/.ssh/id_ed25519_<старое>.pub
```

7. Обновить резервную копию (раздел 12).

Порядок важен: новый ключ ставится и проверяется **до** удаления старого, иначе можно
остаться без доступа.

## 12. Резервное копирование ключей

Приватный ключ существует в единственном экземпляре. Потеря рабочей машины без резервной
копии означает потерю доступа ко всем серверам (останется только аварийная консоль хостера,
которая часто работает плохо).

**Создание зашифрованного архива:**

```sh
cd ~
mkdir -p ssh-keys-backup
cp ~/.ssh/id_ed25519* ~/.ssh/config ssh-keys-backup/
tar czf - ssh-keys-backup | openssl enc -aes-256-cbc -salt -pbkdf2 -out ssh-keys-backup.tar.gz.enc
rm -rf ssh-keys-backup
ls -lah ssh-keys-backup.tar.gz.enc
```

Команда запросит пароль для архива — его нужно запомнить (например, хранить в менеджере
паролей). Подойдёт и любой другой надёжный способ не потерять доступ к этому паролю —
например, сохранить его в текстовом файле и отправить самому себе по почте (с одного
адреса на другой), оставить в черновике письма, или любой другой вариант, при котором
доступ к паролю точно не потеряется. Главное — обязательно подписать, для чего именно
этот пароль, иначе через время будет не разобраться, что он отпирает.

**Проверка, что архив читается** (обязательно — битый бэкап бесполезен):

```sh
openssl enc -d -aes-256-cbc -pbkdf2 -in ssh-keys-backup.tar.gz.enc | tar tzf -
```

Должен вывести список файлов внутри.

**Восстановление:**

```sh
openssl enc -d -aes-256-cbc -pbkdf2 -in ssh-keys-backup.tar.gz.enc | tar xzf -
cp ssh-keys-backup/* ~/.ssh/
chmod 600 ~/.ssh/id_ed25519* ~/.ssh/config
chmod 644 ~/.ssh/*.pub
```

**Где хранить архив:** менеджер паролей (многие поддерживают вложения), зашифрованный
внешний носитель, облако, отправка самому себе по почте с одного адреса на другой,
сохранение в черновике письма, или любой другой вариант, при котором доступ к архиву
точно не потеряется. Главное — **не только на той же машине**, иначе смысл теряется.

⚠️ Незашифрованный приватный ключ в облаке или мессенджере — недопустимо.

## 13. Типовые ошибки

**`Permission denied (publickey)`**
Сервер не принимает ключ. Проверить:

```sh
ssh -v <alias>            подробный лог: какой ключ предлагается
ssh-add -l                загружен ли ключ в агент
```

Если ключа нет в агенте: `ssh-add --apple-use-keychain ~/.ssh/id_ed25519_<имя>`.
Также проверить, что публичный ключ действительно есть в `authorized_keys` на сервере.

**`WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!`**
Отпечаток сервера не совпадает с сохранённым. Штатная причина — сервер переустановлен
или это новая машина на старом адресе. Убрать старую запись:

```sh
ssh-keygen -R <SERVER_IP>
```

Если сервер **не** переустанавливался — это повод разобраться, а не удалять запись
не глядя.

**`Bad owner or permissions on ~/.ssh/config`**
Слишком открытые права. Исправить:

```sh
chmod 600 ~/.ssh/config
chmod 600 ~/.ssh/id_ed25519*
chmod 644 ~/.ssh/*.pub
chmod 700 ~/.ssh
```

**`Too many authentication failures`**
Агент перебирает много ключей и упирается в лимит. Добавить в блок хоста:

```sh
    IdentitiesOnly yes
```

**Запрашивает пароль, хотя ключ настроен**
Проверить `ssh -v <alias>`: возможно, используется не тот ключ (не совпадает
`IdentityFile`), либо права на приватный ключ слишком открыты и SSH его игнорирует.

## 14. Отключение входа по паролю (опционально)

После того как вход по ключу проверен и работает, можно запретить парольную
аутентификацию на сервере:

```sh
cp /etc/ssh/sshd_config /etc/ssh/sshd_config.backup
sed -i 's/^#*PasswordAuthentication.*/PasswordAuthentication no/' /etc/ssh/sshd_config
sed -i 's/^#*PermitRootLogin.*/PermitRootLogin prohibit-password/' /etc/ssh/sshd_config
systemctl restart ssh
```

⚠️ **Не закрывая текущую сессию**, проверить вход из нового окна. При проблеме — откат:

```sh
cp /etc/ssh/sshd_config.backup /etc/ssh/sshd_config && systemctl restart ssh
```

**Стоит ли отключать — вопрос баланса.** Пароль под защитой fail2ban подобрать
практически невозможно, зато он остаётся запасным путём при потере ключа. Если аварийная
консоль у хостера работает плохо, разумнее оставить оба способа: ключ для повседневной
работы, сложный пароль как страховка. От себя — рекомендация для начала оставить оба
варианта, а закрывать вход по паролю уже позже, если после периода уверенной работы
с ключом такая необходимость действительно появится.

## Краткая шпаргалка

```sh
ssh-keygen -t ed25519 -f ~/.ssh/id_ed25519_<имя>     создать ключ
ssh-keygen -p -f ~/.ssh/id_ed25519_<имя>             сменить passphrase
ssh-copy-id -i ~/.ssh/id_ed25519_<имя>.pub root@IP   установить на сервер
ssh-add --apple-use-keychain ~/.ssh/id_ed25519_<имя> сохранить пароль в связке
ssh-add -l                                            какие ключи в агенте
ssh -G <alias>                                        какие параметры применятся
ssh -v <alias>                                        подробный лог подключения
ssh-keygen -R <SERVER_IP>                             убрать хост из known_hosts
```
