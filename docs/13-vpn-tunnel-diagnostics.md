# Диагностика: «VPN перестал работать»

Чеклист проверок, когда туннель лёг. Порядок важен: сначала простые проверки, которые
отсекают ложные версии, потом сложные. Каждый шаг даёт факт, а не догадку.

Документ написан по итогам реального разбора, где на поиск причины ушло много времени
из-за неверных ранних гипотез. Пункты 0-3 существуют именно для того, чтобы этого избежать.

Плейсхолдеры: `<IP_СЕРВЕРА>`, `<ПОРТ>`, `<контейнер>`.

---

## Шаг 0. Откуда проверять (важнее, чем кажется)

**Проверка через домашнюю сеть может обманывать.** Если tproxy заворачивает весь трафик
в туннель, то клиент VPN на телефоне (Shadowrocket и подобные), подключённый к домашнему
Wi-Fi, пойдёт к серверу **через действующий туннель** — двойным туннелем. Он покажет
«работает» независимо от того, доступен ли сервер напрямую.

Достоверные точки проверки:
- **чистая сеть** (без туннелирования) — см. [настройку чистой сети](12-clean-network-vlan.md);
- **мобильный интернет** — другой провайдер, независимый путь;
- **другой сервер** (SSH на VPS) — взгляд «снаружи».

Первым делом ответить: **проверка идёт мимо туннеля или через него?**

---

## Шаг 1. Симптом: что именно не работает

| Что наблюдается | О чём говорит |
|---|---|
| Не открывается ничего, включая домены локального списка | Трафик заворачивается в мёртвый туннель. Проблема в туннеле или конфиге, а не во внешних причинах |
| Домены локального списка открываются, внешние нет | Туннель мёртв, но geoip-разделение работает: локальный список идёт напрямую |
| Всё работает с телефона напрямую, но не через роутер | **Проблема на стороне роутера**: конфиг, версия, правила. Не сетевая недоступность |
| Не работает и через роутер, и напрямую с мобильной сети | Проблема на стороне сервера или сети |

Последние две строки — самое ценное различение. Если один и тот же сервер работает
с другого клиента, сеть и сервер ни при чём.

## Шаг 2. Базовые проверки на роутере

```sh
# Xray вообще запущен и слушает?
ps w | grep '[x]ray' | grep client.json
netstat -tulnp 2>/dev/null | grep 12345

# правила tproxy на месте?
iptables -t mangle -S PREROUTING | grep XRAY

# исключение сервера в цепочке — какой там адрес?
iptables -t mangle -S XRAY | grep RETURN | tail -2

# сколько живых соединений к серверу
conntrack -L 2>/dev/null | grep <IP_СЕРВЕРА> | grep -c ESTABLISHED

# ошибки
tail -30 /opt/xray/log/error.log
```

Ключевое: **адрес в исключении должен совпадать с текущим сервером.** Если там старый IP,
трафик к новому серверу зацикливается сам в себя.

---

## Шаг 3. Конфиг: нет ли «гибрида»

Частая и очень обманчивая причина — конфиг, где смешаны настройки двух транспортов.
Возникает, если конфиг правился патчами (заменой отдельных полей) при смене транспорта.

```sh
jq '.outbounds[]|select(.tag=="proxy")|.streamSettings|keys' /opt/xray/config/client.json
```

Здоровый конфиг содержит **строго один набор**:
- Reality: `network`, `security`, `realitySettings`
- TLS+XHTTP: `network`, `security`, `tlsSettings`, `xhttpSettings`

Если видно одновременно `realitySettings` и `xhttpSettings`, либо `security: "tls"`
рядом с `realitySettings` — конфиг сломан. Симптом: TCP-соединение устанавливается,
но сразу закрывается (в conntrack `CLOSE_WAIT`, обмен 5-7 пакетов).

Лечение: пересобрать outbound целиком — актуальная версия [xray-link](08-xray-link.md)
делает это сама.

---

## Шаг 4. Версии Xray на клиенте и сервере

Расхождение версий даёт симптом, **похожий на сетевой сбой**: с одного клиента сервер
работает, с другого нет.

```sh
# роутер
xray-kernel show
# сервер
docker exec <контейнер> xray version | head -1
```

Если версии разные — привести к одной. Особенно проверять после переустановки сервера:
версия может быть захардкожена в установочном скрипте и молча откатиться назад.

---

## Шаг 5. Сеть: доходит ли до сервера

```sh
# отвечает ли сервер на icmp
ping -c 3 -W 2 <IP_СЕРВЕРА>

# устанавливается ли TCP-соединение
timeout 5 nc <IP_СЕРВЕРА> <ПОРТ> < /dev/null && echo "порт открыт" || echo "порт не отвечает"

# состояние соединений
conntrack -L 2>/dev/null | grep <IP_СЕРВЕРА> | head -5
```

⚠️ Busybox `nc` **не поддерживает `-z` и `-v`** — с этими флагами команда выдаст справку
и ложное «недоступен». Использовать форму выше.

Трактовка состояний в conntrack:

| Состояние | Что значит |
|---|---|
| `SYN_SENT` + `[UNREPLIED]`, ответ 0 пакетов | TCP не устанавливается — недоступность IP:порт или сервер не работает |
| `CLOSE_WAIT`, обмен 5-7 пакетов | Соединение установилось, рукопожатие провалилось — несовпадение протокола/конфига/версий |
| `ESTABLISHED`, счёт растёт | Туннель работает |

Это различение отделяет **сетевую недоступность** (не устанавливается вовсе) от
**проблемы протокола** (устанавливается и рвётся).

## Шаг 6. Проверка снаружи

Проверить тот же порт с другого сервера — так видно, дело в конкретном провайдере
или в сервере вообще:
```sh
# на другом VPS
timeout 5 nc <IP_СЕРВЕРА> <ПОРТ> < /dev/null && echo "открыт снаружи"
```

- **С другого VPS открыт, из дома нет** → проблема на пути через домашнего провайдера.
- **Не открыт нигде** → проблема на сервере (сервис лёг, firewall, хостер).

---

## Быстрая последовательность (памятка)

```
1. Откуда проверяю? Не через ли сам туннель?
2. Домены локального списка работают? (если нет — трафик в мёртвом туннеле)
3. С другого клиента напрямую сервер работает? (если да — дело в роутере)
4. Конфиг: нет ли смеси двух транспортов?
5. Версии Xray совпадают?
6. TCP до сервера устанавливается? (SYN_SENT или CLOSE_WAIT?)
7. С другого VPS порт открыт?
8. Только теперь — гипотеза о фильтрации на узлах связи.
```

---

## Чего не делать

- **Не переустанавливать сервер сразу.** Если сервер работает с другого клиента,
  переустановка ничего не изменит — потеряется время и собьются настройки.
- **Не доверять проверке через домашний Wi-Fi**, когда весь трафик заворачивается
  в туннель: результат будет ложноположительным.
- **Не считать `ping` доказательством доступности** — ICMP может проходить, когда TCP
  к порту не проходит.
- **Не менять несколько вещей сразу** — иначе непонятно, что подействовало.
