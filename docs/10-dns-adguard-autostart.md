# DNS/AdGuard + автозапуск. Детальный отчёт

Продолжение работы после настройки Xray Reality+Vision и tproxy. Здесь описано:
решение проблемы DNS-подмены провайдера, блокировка QUIC, и настройка автозапуска
всей схемы при загрузке роутера.

Принцип документа: **разделять доказанные факты и гипотезы.** «Доказано» = подтверждено
прямым тестом. «Гипотеза» = правдоподобно, но не проверено до конца.

Плейсхолдеры: `<SERVER_IP>` — адрес VDS-сервера, `<ISP_DNS_STUB_IP>` — адрес, на который
провайдер подменяет DNS-ответы для заблокированных доменов.

---

## 1. Проблема: заблокированные сайты не открывались

После настройки туннеля Instagram, LinkedIn, Stanford не открывались (Medium открывался).
Разбор выявил **две наложенные причины**.

### Причина А — DNS-подмена провайдера (доказано)

`nslookup` показал: `instagram.com` и `www.linkedin.com` резолвятся в один и тот же
российский IP-заглушку `<ISP_DNS_STUB_IP>`. Два разных сайта → один российский IP — это
однозначный признак DNS-poisoning: провайдер подменяет DNS-ответы для заблокированных
доменов.

### Причина Б — из-за подмены ломается smart-ru роутинг (доказано debug-логом)

Механизм замкнутого круга:

1. Xray резолвит домен instagram через **системный (отравленный) DNS**;
2. получает заглушку (российский IP);
3. правило роутинга `geoip:ru` видит российский IP → отправляет трафик **direct** (напрямую);
4. напрямую instagram заблокирован → не открывается.

Debug-лог боевого Xray подтвердил дословно:

```
sniffed domain: www.instagram.com
taking detour [direct] for [tcp:www.instagram.com:443]
proxy/freedom: connection opened to ... remote endpoint <ISP_DNS_STUB_IP>:443
```

То есть Xray сам резолвил в заглушку и уводил трафик мимо туннеля.

Почему Medium открывался: его настоящий IP (Cloudflare) провайдер не травит, Xray получал
верный IP и гнал через туннель.

## 2. Решение DNS — AdGuard Home с DoH + DNS-секция в Xray

### Шаг 1 — AdGuard Home с DoH-upstream (на роутере)

AdGuard Home уже встроен в прошивку GL.iNet (`/usr/bin/AdGuardHome`, конфиг
`/etc/AdGuardHome/config.yaml`). Был **выключен**. Включён через веб-панель
(APPLICATIONS → AdGuard Home → Enable), опция «Handle Client Requests» оставлена
**выключенной** (чтобы не менять сразу два параметра и не ломать доменный роутинг).

В конфиге AdGuard upstream заменён с открытых `8.8.8.8 / 9.9.9.9` на **зашифрованные DoH**:

```yaml
upstream_dns:
  - https://cloudflare-dns.com/dns-query
  - https://dns.quad9.net/dns-query
```

Провайдер не может ни прочитать, ни подменить DoH. После рестарта AdGuard
(`/etc/init.d/adguardhome restart`) `nslookup instagram.com 127.0.0.1` стал возвращать
**настоящий** IP `157.240.205.174` вместо заглушки. DNS-подмена устранена.

Схема DNS на роутере: `клиент → dnsmasq (:53) → AdGuard (:3053) → DoH`.
AdGuard слушает DNS на порту 3053, dnsmasq на :53 форвардит на него. Веб-морда AdGuard — :3000.

### Шаг 2 — DNS-секция в Xray (критично)

Даже с чистым AdGuard оставалась проблема: **сам Xray резолвил через системный DNS**
(отравленный), а не через AdGuard. Нужно было заставить Xray резолвить чисто.

**Тупиковая попытка (что не работает):** DNS-секция с внешним DoH напрямую:

```json
{ "dns": { "servers": ["https://cloudflare-dns.com/dns-query"] } }
```

Это **сломало резолвинг целиком** — весь интернет лёг. Причина: Xray, чтобы обратиться
к `cloudflare-dns.com`, должен сначала резолвить сам этот домен — а bootstrap не задан
(замкнутый круг), плюс DoH-трафик Xray мог сам зацикливаться в маршрутизации.
Восстановлено из бэкапа.

**Рабочее решение** — DNS-секция с **локальным** резолвером:

```json
{
  "dns": {
    "servers": ["127.0.0.1"],
    "queryStrategy": "UseIPv4"
  }
}
```

Теперь Xray резолвит через `127.0.0.1` → dnsmasq → AdGuard → DoH, получает **чистый** IP.
Никакого bootstrap не нужно (127.0.0.1 — это IP, резолвить нечего), зацикливания нет.
Результат: instagram резолвится в `157.240.x` → `geoip:ru` не срабатывает → трафик идёт
через туннель. Debug-лог подтвердил смену `[direct]` на `[proxy]`.

**Урок:** для DNS-резолвинга Xray на роутере с локальным AdGuard — использовать `127.0.0.1`,
а не внешний DoH напрямую. Проще, надёжнее, без циклов.

## 2b. Российские госдомены через Яндекс DoH (доработка)

**Проблема (обнаружена позже):** сайт налоговой `lkfl2.nalog.ru` не открывался в сети роутера
(`nslookup` давал `SERVFAIL` / timeout), хотя с мобильного интернета работал.

**Диагностика (доказано):**

- через основную цепочку (Cloudflare DoH) — timeout, домен не резолвится;
- через `1.1.1.1` напрямую — тоже timeout;
- через Google `8.8.8.8` и Яндекс `77.88.8.8` — резолвится нормально:
  `lkfl2.nalog.ru → CNAME lkfl21.gi.nalog.ru → 213.24.64.175`.

**Причина:** Cloudflare DoH (основной upstream) **не резолвит некоторые российские
госдомены** (`.gi.nalog.ru` — внутренняя инфраструктура ФНС). Российские DNS их резолвят.

**Решение:** per-domain upstream в AdGuard — вся зона `.ru` резолвится через **Яндекс DoH**,
остальное через Cloudflare/Quad9. В `/etc/AdGuardHome/config.yaml`, первой строкой в
`upstream_dns`:

```yaml
upstream_dns:
  - "[/ru/]https://common.dot.dns.yandex.net/dns-query"
  - https://cloudflare-dns.com/dns-query
  - https://dns.quad9.net/dns-query
```

Синтаксис `[/ru/]сервер` = «домены зоны .ru резолвить через этот сервер». После рестарта
AdGuard `lkfl2.nalog.ru` резолвится в `213.24.64.175`, сайт открывается. instagram при этом
по-прежнему резолвится через Cloudflare (`31.13.x` / `157.240.x`) — разделение работает.

**Вывод на будущее:** российские домены лучше резолвить российским DNS. Правило `[/ru/]`
покрывает всю зону — если всплывут другие госсайты, они тоже будут резолвиться корректно.

## 3. Блокировка QUIC (UDP 443)

Instagram/LinkedIn предпочитают QUIC (HTTP/3 поверх UDP 443). QUIC через tproxy-туннель
работал нестабильно — браузер долго ждал ответа по QUIC и не откатывался на рабочий TCP.

**Тупик:** правило в `FORWARD` не сработало — tproxy перехватывает трафик в `PREROUTING`
**раньше**, чем он доходит до FORWARD.

**Рабочее решение** — DROP в таблице `raw/PREROUTING` (обрабатывается до tproxy):

```sh
iptables -t raw -I PREROUTING -i br-lan -p udp --dport 443 -j DROP
```

Браузер, не получив ответа по QUIC, откатывается на TCP, который через туннель работает.

Примечание: сам по себе QUIC-блок instagram не открыл (главная причина была в DNS, см. п.2),
но он нужен для стабильности — без него часть браузеров висит на QUIC.

## 4. Автозапуск (init.d + procd)

**Проблема:** вся схема (Xray, tproxy-правила, QUIC-блок, policy-routing) держалась вручную
и слетала при перезагрузке.

**Решение** — два файла:

1. **`/opt/xray/tproxy-apply.sh`** (в этом репозитории: `scripts/01-tproxy-apply.sh`) —
   идемпотентный скрипт: чистит старые правила, затем ставит tproxy-цепочку + QUIC-блок +
   policy-routing. Безопасен для повторного запуска.

2. **`/etc/init.d/xray-tproxy`** (в этом репозитории: `scripts/08-xray-tproxy`) —
   init.d-сервис (procd): при загрузке запускает Xray (с автоперезапуском `respawn`),
   ждёт 8 сек готовности, применяет `tproxy-apply.sh`. При остановке — снимает правила
   через `tproxy-flush.sh` (`scripts/02-tproxy-flush.sh`).

Отдельно — хук **`/etc/firewall.user`** (в этом репозитории: `scripts/07-firewall.user`):
fw3 при любой пересборке правил (изменение WAN, правки в веб-панели, reload любым сервисом)
стирает таблицу mangle целиком — вместе с tproxy-правилами. Без этого хука туннель после
каждой такой пересборки молча умирал до ручного перезапуска. Хук переприменяет
`tproxy-apply.sh`, если Xray уже запущен; если ещё не запущен (например, во время загрузки,
когда fw3 стартует раньше init.d-сервиса) — не трогает, правила применит сам init.d-сервис
после старта Xray.

Приоритет запуска `START=95` (поздний — после сети и firewall). Включён в автозагрузку:

```sh
/etc/init.d/xray-tproxy enable
```

Создаёт симлинки `S95xray-tproxy` (старт) и `K10xray-tproxy` (стоп) в `/etc/rc.d/`.

**Проверено реальной перезагрузкой:** после `reboot` вся схема поднялась сама — Xray запущен,
порт 12345 слушается, правила на месте (2 TPROXY / 1 QUIC / 1 policy-rule), сервис `running`,
сайты открываются. Автозапуск надёжен.

## 5. Итоговая рабочая схема

```
LAN-клиент (за MikroTik)
   │
   ├─ DNS → dnsmasq(:53) → AdGuard(:3053) → DoH:
   │        .ru  → Яндекс DoH (common.dot.dns.yandex.net)   [РФ-домены, вкл. госсайты]
   │        всё остальное → Cloudflare / Quad9 DoH          [чистый IP, без подмены]
   │
   └─ трафик → tproxy(PREROUTING) → Xray(:12345)
                                       │
                    ┌──────────────────┴───────────────────┐
              sniffing домена                        (QUIC UDP443 → DROP в raw)
                    │
          routing (smart-ru):
            .ru / geoip:ru / РФ-домены → direct (напрямую)
            остальное → proxy → VLESS+Reality+Vision → <SERVER_IP>:443 → Эстония
                                  (fingerprint: randomized)
```

Xray резолвит домены через `127.0.0.1` (AdGuard→DoH) → заблокированные получают настоящий IP
→ идут через туннель. Всё поднимается автоматически при загрузке.

---

## 6. Краткие выводы

- Заблокированные сайты (instagram/linkedin/stanford) **открываются**.
- Причина была двойная: DNS-подмена провайдера + из-за неё ошибочный роутинг в direct.
- Решение: AdGuard с DoH + DNS-секция в Xray через `127.0.0.1`.
- QUIC блокируется в raw/PREROUTING → браузеры на TCP.
- Автозапуск через init.d/procd, проверен перезагрузкой — схема постоянна.
