# WireGuard-сервер: удалённый доступ к домашней сети

Решение, к которому пришли после отказа от Tailscale (см.
[попытку с Tailscale](16-tailscale-exit-node-attempt.md)). Используется белый
статический IP от провайдера — прямое подключение, без CGNAT, без релеев, без
сторонних сервисов.

Плейсхолдеры: `<HOME_WHITE_IP>` — белый статический IP дома, `<SERVER_IP>` — адрес
VDS, `<WAN_PRIVATE_IP>` — приватный адрес WAN-интерфейса роутера до NAT провайдера.

---

## Что даёт

Клиент (телефон/ноутбук/планшет) из любой точки мира подключается к домашнему
роутеру и получает:

1. **Доступ к домашней сети** — 192.168.8.0/24 (веб-панель роутера, устройства дома).
2. **Единая маршрутизация** — трафик клиента обрабатывается теми же правилами, что и трафик домашних устройств: разделение по geoip работает одинаково.
3. **DNS через AdGuard роутера** — блокировка рекламы работает и вне дома.

Проверено: телефон с мобильного интернета → открывается веб-панель роутера,
маршрутизация работает так же, как для домашних устройств. Память Xray под
нагрузкой — несколько видеопотоков 4K одновременно — пик 63 МБ, стабильно, без OOM.

---

## Ключевое условие: белый статический IP

Работает благодаря белому IP `<HOME_WHITE_IP>` (бизнес-статик от провайдера, без
дополнительной платы).

Важный нюанс: на WAN роутера стоит приватный адрес `<WAN_PRIVATE_IP>` (proto
static), а наружу роутер выходит как `<HOME_WHITE_IP>`. Провайдер выполняет 1:1
NAT. Входящие соединения на белый IP доходят до роутера — это проверено с
внешнего VPS. Именно поэтому WireGuard работает: клиент подключается напрямую к
`<HOME_WHITE_IP>:51820`.

---

## Архитектура

```
Телефон (мобильный интернет / сторонний Wi-Fi)
   │  WireGuard, UDP 51820
   ▼
<HOME_WHITE_IP>  (белый IP, 1:1 NAT провайдера)
   ▼
GL-MT5000  eth1 (<WAN_PRIVATE_IP>)
   ▼
wg0  (10.0.100.1/24)   ← клиент получает 10.0.100.2, .3, ...
   │
   ├─► домашняя сеть 192.168.8.0/24     (wg0 в зоне firewall 'lan')
   │
   └─► tproxy (PREROUTING -i wg0 -j XRAY)
         ├─► внешний трафик → Xray → VDS <SERVER_IP>
         └─► локальный список (geoip) → напрямую через провайдера
```

Ключевой момент: `wg0` добавлен и в **зону lan** (доступ к домашней сети + выход
в интернет), и в **перехват tproxy** (общие правила маршрутизации). Оба — автоматически,
переживают reboot.

---

## Что настроено (компоненты)

### 1. Интерфейс wg0 (UCI, /etc/config/network)

- `proto='wireguard'`, `listen_port='51820'`, адрес `10.0.100.1/24`;
- приватный ключ сервера — в UCI;
- peers (клиенты) — секции `wireguard_wg0`, каждый со своим public_key,
  preshared_key, allowed_ips (`10.0.100.X/32`), `persistent_keepalive=25`.

### 2. Firewall (UCI, /etc/config/firewall)

- `wg0` добавлен в **зону lan** (`firewall.@zone[0].network` = `'lan' 'wg0'`) →
  даёт клиентам доступ к домашней сети и выход в интернет через существующие
  правила;
- правило **Allow-WireGuard-WAN**: `src=wan, proto=udp, dest_port=51820,
target=ACCEPT` → открывает порт на белом IP.

### 3. Перехват в tproxy (/opt/xray/tproxy-apply.sh)

```sh
WG_IF="wg0"
...
if ip link show "$WG_IF" >/dev/null 2>&1; then
    iptables -t mangle -A PREROUTING -i "$WG_IF" -j XRAY
fi
```

Ставится автоматически при старте сервиса `xray-tproxy` (и при reload fw3 через
`firewall.user`). Условие `if ip link show` безопасно, если WG выключен.

### 4. Ключи сервера

`/etc/wireguard-manual/server_private.key` и `server_public.key` (права 600).
Приватный ключ сервера удалять нельзя — без него WG не поднимется.

---

## Управление клиентами: скрипт wg-client

Установлен как `/opt/xray/wg-client.sh`, симлинк `/usr/bin/wg-client`. В этом
репозитории: `scripts/09-wg-client.sh`.

```sh
wg-client add <имя>     создать клиента (ключи, свободный IP, готовый .conf)
wg-client purge <имя>   стереть .conf с роутера (клиент продолжает работать)
wg-client del <имя>     удалить клиента полностью
wg-client list          список клиентов + статус подключения
wg-client qr <имя>      QR-код (для телефонов/планшетов)
wg-client show <имя>    путь к конфигу + команда scp для Mac
```

Особенности реализации:

- свободный IP выбирается автоматически (10.0.100.2 .. .254);
- peer добавляется **на лету** через `wg set` (без `network reload`) —
  существующие подключения других клиентов не рвутся;
- одновременно сохраняется в UCI → переживает reboot;
- конфиги клиентов: `/etc/wireguard-manual/clients/<имя>.conf` (права 600).

### Рекомендуемый порядок (безопасность)

1. **Создать клиента:**
   `wg-client add macbook`
2. **Перенести файл `.conf` на устройство:**
   - **Mac / Ноутбук:** Перенесите файл по SCP:

     ```sh
     scp -O root@192.168.8.1:/etc/wireguard-manual/clients/macbook.conf ~/Downloads/
     ```

   - **Телефон:** Вывести QR-код и отсканировать его официальным приложением WireGuard:
     `wg-client qr macbook`

3. **Дополнительная мера безопасности:** Стереть приватный ключ с роутера:
   `wg-client purge macbook`

Почему `purge`: по канонам WireGuard приватный ключ клиента должен существовать
только на самом клиенте. Серверу для работы нужен лишь публичный ключ (он в UCI).
Хранение приватных ключей всех клиентов на роутере — лишний риск при его
компрометации. Если конфиг понадобится снова — пересоздать клиента (`del` +
`add`), это несколько секунд.

---

## Конфиг клиента (структура)

```
[Interface]
PrivateKey = <приватный ключ клиента>
Address = 10.0.100.X/32
DNS = 10.0.100.1            ← DNS через роутер (AdGuard: блокировка рекламы вне дома)

[Peer]
PublicKey = <публичный ключ сервера>
PresharedKey = <PSK>        ← дополнительный слой защиты
Endpoint = <HOME_WHITE_IP>:51820
AllowedIPs = 0.0.0.0/0      ← весь трафик клиента через домашний шлюз
PersistentKeepalive = 25
```

`AllowedIPs = 0.0.0.0/0` — принципиально: весь трафик клиента идёт через дом, где
tproxy разделяет его по правилам маршрутизации.

---

## Известные особенности

- **Из домашнего Wi-Fi WG не подключается.** Это NAT loopback (hairpin) —
  подключение к своему же внешнему IP изнутри своей сети. Нормальное поведение,
  не ошибка. Дома WG и не нужен — устройства уже в домашней сети и ходят через
  тот же Xray.
- **Смена белого IP.** Если провайдер когда-либо сменит IP, поправить
  `ENDPOINT_HOST` в `wg-client.sh` и перевыпустить конфиги клиентов. IP
  статический и бессрочный, так что это надолго.
- **Если провайдер отключит белый IP.** На этот случай параллельно настроен
  независимый резервный путь через wg-easy на VDS — см.
  [«Роутер как WireGuard-клиент VPS»](19-router-as-wg-client.md).

## Проверка после перезагрузки (всё поднимается само)

```sh
ip addr show wg0 | grep inet                     # 10.0.100.1/24
wg-client list                                   # клиенты на месте, статус подключения
iptables -t mangle -S PREROUTING | grep XRAY     # br-lan + wg0
iptables -S | grep 51820                         # порт открыт на WAN
ps w | grep '[x]ray' | grep client.json          # Xray работает
```

Проверено: после reboot всё поднимается автоматически, без единой ручной команды.

## Почему WireGuard, а не Tailscale (инженерный вердикт)

|                    | WireGuard (принято)               | Tailscale (откачен)                           |
| ------------------ | --------------------------------- | --------------------------------------------- |
| Подключение        | прямое к белому IP                | через DERP-релей (двойной CGNAT)              |
| Где работает       | в ядре Linux (лёгкий)             | userspace-демон (раздувался до 645 МБ → OOM)  |
| Мобильный сценарий | работает                          | не работал (relay timeout)                    |
| Приватность        | свои ключи, никаких третьих лиц   | зависит от координационного сервера Tailscale |
| Поддержка GL.iNet  | штатная (kmod + tools в прошивке) | бета, глючная                                 |

Tailscale создан для работы без белого IP. При наличии рабочего белого IP
он становится ненужным. Подробности попытки — в
[отдельном документе](16-tailscale-exit-node-attempt.md).
