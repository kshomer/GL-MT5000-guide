# Скрипты-инструменты и разбор проблемы TIME_WAIT

Документ описывает набор управляющих скриптов, созданных для роутера MT5000,
и детальный разбор проблемы накопления TIME_WAIT-соединений (диагностика и решение).

Плейсхолдеры: `<IP_сервера>` — адрес VDS-сервера.

---

## 1. Набор скриптов-инструментов

Все скрипты лежат в `/opt/xray/`, имеют симлинки в `/usr/bin/` (короткий вызов,
переживают перезагрузку), работают через `jq`, валидируют изменения и откатываются при ошибке.

| Скрипт | Симлинк | Назначение | В этом репозитории |
|---|---|---|---|
| `xray-route.sh` | `xray-route` | Исключения маршрутизации (сайт через туннель / напрямую) | `scripts/03-xray-route.sh` |
| `xray-link.sh` | `xray-link` | Смена сервера по vless-ссылке | `scripts/04-xray-link.sh` |
| `xray-kernel.sh` | `xray-kernel` | Смена версии ядра Xray (с GitHub, с автооткатом) | `scripts/05-xray-kernel.sh` |
| `xray-geoupdate.sh` | `xray-geoupdate` | Обновление geodata (geoip/geosite) | `scripts/06-xray-geoupdate.sh` |

Подробности по каждому — в отдельных документах.

Общие принципы всех скриптов:
- изменения через `jq` (JSON как структура, не ломается);
- валидация через `xray -test` перед применением;
- бэкап перед изменением, автооткат при ошибке;
- fingerprint при смене ссылки принудительно `randomized` (chrome ломает связку под нагрузкой);
- IP сервера везде берётся динамически из конфига (единый источник правды).

## 2. Проблема TIME_WAIT — диагностика и решение

### Симптом

При частой смене версии ядра (или частых рестартах сервиса) заграничные сайты переставали
открываться. Плавающе — иногда после смены версии, иногда нет. Повторный рестарт «лечил».
Прогрев (ожидание до 88 сек) НЕ помогал.

### Ложные версии (отброшены по фактам)

- **Прогрев туннеля** — отброшено: при ожидании 88 сек проблема сохранялась так же, как при 12.
  Ключевое наблюдение: «если работает — работает сразу, если нет — то и через 88 сек нет».
  Значит дело не во времени поднятия.
- **Версия ядра** — отброшено: сама версия 26.6.22 исправна (проходит version + test,
  туннель на ней поднимается). Проблема не в бинаре.
- **Задвоение iptables-правил** — отброшено: проверка показала XRAY-цепочку в PREROUTING
  ровно 1 раз, счётчики TPROXY растут, привязка корректна.

### Истинная причина (доказана ловушкой)

Диагностическая ловушка (скрипт, непрерывно проверявший туннель и снявший снимок в момент
сбоя) поймала состояние в активной фазе сбоя:

```
conntrack к серверу: всего 1723, из них TIME_WAIT 1665, работающих 4
```

**1665 соединений в состоянии TIME_WAIT к одному серверу.** Это и есть причина.

Механизм:
1. Vision (`xtls-rprx-vision`) открывает отдельное TCP-соединение на каждый поток.
2. При рестарте старый Xray убивается — все его соединения (сотни) разом закрываются и
   уходят в TIME_WAIT на ~120 секунд (стандартный TCP-таймаут).
3. При частых рестартах С активным трафиком TIME_WAIT накапливается до тысяч.
4. TIME_WAIT занимает пару «исходящий порт ↔ сервер:443». Когда их полторы тысячи —
   исчерпывается пул исходящих портов к серверу (усугублено CGNAT провайдера).
5. Новые соединения к серверу не могут получить свободный порт → туннель не встаёт.

Debug-лог подтвердил: запрос принимался (`accepted ... [socks >> proxy]`), но соединение к
серверу не открывалось (нет `connection opened`) — именно из-за нехватки портов.

Почему прогрев не лечил: TIME_WAIT висит фиксированные ~120 сек, ожидание внутри этого окна
порты не освобождает. Почему рестарт «лечил»: на самом деле проходило время, часть TIME_WAIT
истекала. Почему плавающе: зависит от того, сколько TIME_WAIT накопилось к моменту.

### Решение (встроено в tproxy-apply.sh)

При каждом применении правил (а `tproxy-apply.sh` вызывается при любом рестарте — через любой
скрипт и при загрузке) выполняется очистка мёртвых TIME_WAIT-соединений к серверу:

```sh
conntrack -D -d <IP_сервера> -p tcp --state TIME_WAIT
```

Удаляются ТОЛЬКО TIME_WAIT (мёртвые), ESTABLISHED (активные) не трогаются. Это освобождает
порты сразу, не дожидаясь истечения таймаута. Проверено: после серии рестартов TIME_WAIT = 0,
туннель работает.

### Важно: в обычной жизни проблемы бы не было

Накопление до критического уровня требует ДЕСЯТКОВ рестартов подряд С активным трафиком —
это возникло только из-за интенсивного тестирования. При обычной эксплуатации (смена версии
раз в месяц) TIME_WAIT от предыдущего рестарта давно истекает, проблемы нет. Очистка в
tproxy-apply.sh — это страховка от интенсивного сценария, работающая автоматически.

### Дополнительные защиты в xray-kernel

Помимо очистки conntrack, скрипт смены версии `xray-kernel` имеет активную проверку туннеля
с автоповтором: после смены он реально проверяет, идёт ли трафик через сервер, и при неудаче
делает повторный restart (до 3 попыток), а если туннель так и не встал — автооткат на
предыдущую версию. Это ловит проблему независимо от причины.
