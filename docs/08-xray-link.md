# xray-link — смена VPN-сервера по vless-ссылке

Скрипт меняет сервер в конфиге Xray на роутере: разбирает vless-ссылку, пересобирает
outbound, перезапускает сервис, дожидается готовности туннеля и при неудаче откатывается.

Расположение: `/opt/xray/xray-link.sh`, симлинк `/usr/bin/xray-link`.
В этом репозитории: `scripts/04-xray-link.sh`.

---

## Команды

```sh
xray-link                        показать текущий сервер и статус
xray-link show                   то же
xray-link "vless://..."          сменить сервер (ссылка ОБЯЗАТЕЛЬНО в кавычках)
xray-link --fp=<fp> "vless://…"  сменить + задать fingerprint вручную
xray-link rollback               вернуть предыдущий конфиг
```

Кавычки вокруг ссылки обязательны: без них оболочка разберёт `&` как фоновый запуск
и параметры потеряются.

---

## Поддерживаемые транспорты

| security | type | обязательные параметры ссылки |
|---|---|---|
| reality | tcp | `pbk` (publicKey), `sid` (shortId) |
| tls | xhttp | `path` |
| tls | ws | `path` (по умолчанию `/`) |
| tls | grpc | `serviceName` |
| tls | tcp | — |

Дополнительно распознаются: `sni`, `flow`, `fp`, `host`, `mode`, `spx`.

---

## Почему outbound пересобирается целиком

Блок `proxy` в конфиге собирается **с нуля** по типу ссылки, а не патчится по отдельным
полям (адрес, UUID, ключи). Это принципиально при смене транспорта: если бы поля
дописывались поверх уже существующего конфига, при переходе, например, с XHTTP на Reality
одновременно остались бы `security: "tls"`, старые `xhttpSettings` и новые
`realitySettings` — Xray выполнял бы обычное TLS-рукопожатие, а сервер ждал бы Reality.
Соединение устанавливалось бы и тут же рвалось (в conntrack `CLOSE_WAIT`, обмен 5-7
пакетов) — причём с телефона через тот же сервер всё продолжало бы работать нормально, что
выглядело бы как блокировка провайдером именно на роутере, а не как проблема конфига.

Полная пересборка исключает этот сценарий: остатки предыдущего транспорта физически не
могут сохраниться в новом блоке.

## Особенности реализации

**flow только для tcp.** Параметр `xtls-rprx-vision` применим к TCP-транспорту.
Для xhttp/ws/grpc он игнорируется с предупреждением — Xray с такой комбинацией не работает.

**fingerprint по умолчанию `randomized`.** Значение `fp` из ссылки намеренно игнорируется:
на этом роутере fingerprint `chrome` доказанно ломает связку под нагрузкой (выяснено при
отладке Reality). Если нужно другое значение — флаг `--fp=`.

**Двухфазное ожидание туннеля.** Появление первого соединения ещё не значит готовность:
при 1-3 соединениях клиентский трафик обычно не идёт, при 5+ уже работает. Одного факта
первого соединения недостаточно для вывода о готовности — поэтому скрипт сначала дожидается
первого соединения (до 45 сек), затем даёт время на прогрев (до 40 сек) и только после
этого подтверждает готовность туннеля.

**Автооткат.** Если туннель не поднялся — возвращается предыдущий конфиг, а нерабочий
сохраняется в `client.json.failed` для разбора.

**tproxy подхватывает адрес сам.** Скрипт `tproxy-apply.sh` читает адрес сервера из конфига
и, если там домен, резолвит его в IP (iptables принимает только адреса).

**Что НЕ трогается:** inbound tproxy, routing (geoip-разделение), DNS, outbound direct/block.

## Настраиваемые параметры (в шапке скрипта)

```sh
WAIT_TUNNEL=45     сколько ждать появления первого соединения
WARMUP=40          сколько ещё ждать прогрева после первого соединения
MIN_EST=5          сколько соединений считаем признаком готового туннеля
DEFAULT_FP=randomized
```

## Про число соединений

VLESS с Vision открывает **отдельное TCP-соединение на каждый поток** — не мультиплексирует
всё в один канал. Браузер, открывая страницу, создаёт десятки параллельных запросов, отсюда
десятки соединений. Трафик стих — соединения закрываются по таймауту, счётчик падает.

Ориентиры:
- **0** — туннеля нет;
- **1-3** — только поднимается, клиентский трафик ещё не идёт;
- **5-20+** — работает нормально;
- колебания при обычном серфинге — норма.

Это индикатор активности, а не пропускной способности. Используется как признак готовности
за неимением более прямого способа: прямой `curl` с роутера идёт мимо tproxy и о состоянии
туннеля ничего не говорит.

## Согласованность версий Xray

**Версии на сервере и на роутере должны совпадать.** Расхождение даёт симптом, неотличимый
от блокировки провайдером: с одного клиента сервер работает, с другого нет.

Проверка:
```sh
# на роутере
xray-kernel show
# на сервере (Docker)
docker exec <контейнер> xray version | head -1
```

Обновление на новую версию:
1. на сервере — поменять тег образа в compose, `docker compose pull && docker compose up -d`;
2. на роутере — `xray-kernel update <та же версия>` (скачает, проверит туннель, откатится сам при неудаче);
3. проверить доступ.

Если версия захардкожена в установочном скрипте сервера — не забыть поправить и там,
иначе переустановка молча вернёт старую.

## Типовые сценарии

**Посмотреть, что сейчас настроено:**
```sh
xray-link show
```

**Переключиться на резервный сервер:**
```sh
xray-link "vless://..."
# дождаться сообщения о прогреве, проверить доступ
```

**Вернуться назад:**
```sh
xray-link rollback
```

**Если после нескольких переключений подряд туннель не поднимается:**
```sh
/etc/init.d/xray-tproxy restart
# подождать ~45 сек
```
Частые перезапуски подряд иногда оставляют Xray в состоянии, из которого помогает
выйти дополнительный перезапуск.
